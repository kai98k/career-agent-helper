# Day 06｜先有測試案例，再談 AI 準不準：建立虛構履歷與職缺資料集

> Recap: 昨天把 `/analyze` 接上了單頁 HTML，貼履歷、按按鈕、看結果，流程終於是通的

但我測試的方式還停在「貼一份履歷進去，看一下輸出，覺得還不錯」

「覺得還不錯」有兩個問題
第一，我每次貼的履歷都不一樣，結果好壞分不出是 prompt 變好還是輸入變簡單
第二，「不錯」不是一個可以寫進報表的東西

今天不碰模型，先把地基挖出來：一批固定的、可以重複跑的測試資料

## 為什麼這件事排在第 6 天

因為再晚就來不及了

Day 07 開始要動 schema，Day 09 要做證據比對，Day 10 要做不捏造的改寫
這三天每一天都會改 prompt，而每改一次我都要回答同一個問題：**這次比上次好嗎？**

要回答它，輸入必須是固定的
prompt 是變因，資料是控制組，這是國中理化就教過的事

資料集晚一天做，前面那幾天的改動就全部沒有基準線可以回頭比

## 全部虛構，沒有例外

先講最硬的那條規則：**這批資料裡不會有任何真實履歷，包含我自己的**

這不只是隱私潔癖，是三個很實際的理由

- 履歷是高敏感個資，姓名、電話、學經歷、公司全都在上面。真實履歷一旦進了 repo，就是永久的
- 我要把這個系列公開，資料集必須能跟著公開。不能公開的資料集，別人重現不了，Day 30 的重現指南等於白寫
- 我自己的履歷只有一份，而且只涵蓋一種職能。我需要的是十種

所以聯絡方式一律用保留號段與保留網域：

```
Email: kewei.lin@example.invalid
電話: 0900-000-002
```

`.invalid` 是 RFC 2606 保留給「保證不會存在」的頂級網域，寄不出去也不會誤撞到真人
公司名也全部是捏造的，`data/index.json` 開頭就寫明這件事：

```json
"notice": "本資料集內所有姓名、公司、聯絡方式皆為虛構，不對應任何真實個人或企業。email 一律使用 @example.invalid，電話使用 0900-000-00X 保留號段。僅供分析品質測試與評估基準使用。"
```

### 順手把手滑的路堵起來

Day 08 要做 PDF 上傳，測試的時候我很可能會隨手丟一份真的 PDF 到 `data/resumes/` 底下試抽取
然後某一天 `git add .`，它就上去了

所以 `data/resumes/.gitignore` 寫成先全擋、再逐一放行：

```gitignore
# 預設不追蹤這個目錄下的任何履歷檔案。
# 這裡可能放著用來測試抽取的真實 PDF，真實履歷是高敏感個資，不進版控。
*

# 例外：確認過是虛構資料的測試素材，用 sample- 前綴，逐一放行。
!.gitignore
!.gitkeep
!sample-*.txt
!sample-*.pdf
```

白名單比黑名單安全
黑名單漏掉一種情況就外洩，白名單漏掉一種情況只是東西沒進版控，我會馬上發現

## 資料不是生越多越好，是每一份都要有工作

原本的計畫是「做 8 到 12 份涵蓋不同職能與資歷的履歷」
真的動手才發現，數量根本不是重點

如果十份履歷都是寫得很完整、條理分明的好履歷，那這個資料集只能測出一件事：模型在理想輸入下能不能跑

可是真實世界的履歷不長那樣
所以我反過來做：**先列出「我想測模型哪個毛病」，再為每個毛病生一份履歷**

最後變成五種標記：

| 標記 | 這份履歷長什麼樣 | 想測出模型的什麼問題 |
| --- | --- | --- |
| `vague` | 全篇只有「負責開發」「協助專案」，沒有任何可驗證的細節 | 會不會自己腦補出不存在的技術細節 |
| `quantified` | 原文就寫滿 QPS、P99、覆蓋率等具體數字 | 會不會改寫或誇大原文的數字 |
| `skill_gap` | 職稱與技能清單明顯不相稱，缺該職能的核心技能 | 看不看得出核心能力缺席 |
| `timeline_gap` | 經歷之間有沒說明的空白期 | 抓不抓得到 |
| `explained_gap` | 有空白期，但履歷裡已經說明原因 | 會不會**誤判**成隱瞞 |

最後兩個是一組對照，這組是整份資料集我最在意的
`timeline_gap` 測的是漏抓（false negative），`explained_gap` 測的是誤判（false positive）

只放前者，我會把模型調得越來越多疑，然後對每個轉職者都吐出一句「有未說明的空白期」
方之晴這份履歷的空白期，原文寫得清清楚楚：

```
（2021/06 - 2024/08 期間因家中長輩照護需求離開職場，後期開始自學程式。）
```

模型如果還把它列成疑點，那不是嚴謹，那是沒讀完
`index.json` 裡我直接把這句寫進備註：「模型若當成負面疑點即為誤判」

`vague` 跟 `quantified` 也是一組
林可薇那份四年後端，三段經歷九條 bullet，沒有一條有技術名詞、規模或成果：

```
明曜資訊  後端工程師  2022/03 - 迄今
- 負責公司產品的系統開發與維護
- 協助各項專案順利進行，與前端及 PM 密切配合
- 處理線上問題並進行修正
```

這份是給模型的誘惑題
「四年後端 + Python + MySQL + Docker」很容易被補成「具備四年微服務開發經驗」
但原文沒有微服務三個字。Day 09 做證據比對的時候，這份會是第一個被拿去跑的

最後的組成是 **10 份履歷、6 份職缺**
職能涵蓋後端（1 / 4 / 8 年）、前端（2 / 5 年）、資料工程、QA、DevOps、轉職者、應屆

## 真正的重點是答案卷

做到這裡只完成一半

十份履歷、六份職缺，只是**輸入**
沒有標準答案的輸入叫素材，有標準答案的才叫測試集

所以 `data/index.json` 裡還有第三段：`expected_matches`，24 組人工標註的期望結果

```json
{
  "resume": "sample-data-engineer-3y.txt",
  "job": "sample-job-data-platform.txt",
  "expected_fit": "partial",
  "reason": "職稱與年資相符，Python / pandas 可對上必備第 5 項，但缺 SQL 佐證、無資料倉儲建模、無排程工具、無雲端資料倉儲，7 項必備僅命中 1-2 項。這組是測試「職稱吻合但實質落差大」的關鍵樣本。"
}
```

`reason` 欄不是給程式讀的，是給我自己讀的
半年後我一定不記得當初為什麼標 `partial`。跑評估時看到模型不同意，我要能在三秒內判斷是模型錯還是我錯

### 三組我刻意埋的陷阱

**職稱對上、實質落差大**：蘇宜臻的職稱就是資料工程師，年資也符合，投資料平台職缺看起來天生一對
但她技能欄沒有 SQL、沒有 Airflow、沒有任何資料倉儲。只比對職稱跟年資的話會給 strong

**技能全中，但不該媒合**：黃詠翔（8 年 Tech Lead）對上初階後端職缺，我標 `weak`
六項必備條件他全部超出，關鍵字比對會給滿分。但年資與薪資區間差太遠，實務上這個媒合不會發生
這組測的是模型有沒有「適配」的概念，而不是「涵蓋」的概念

**非典型但該給高分**：方之晴自學一年，對上初階後端職缺，我標 `strong`
因為那個職缺明文寫「或具備可展示的完整專案作品」，而她的訂位系統真的上線給兩家門市用過三個月
只看年資欄位會給 weak，讀完職缺條件才會給 strong

### 為什麼只有三級，不打分數

`fit_scale` 只有 strong / partial / weak：

```json
"fit_scale": {
  "strong": "條件大致吻合，必備條件缺漏 0-1 項，可直接進入面試",
  "partial": "方向相符但有明顯落差，必備條件缺 2-3 項或年資不足",
  "weak": "職能或年資明顯不符，不建議投遞"
}
```

我原本想標 0 到 100 分，寫了三組就放棄了
同一份履歷我今天標 72 分，明天可能標 65 分，這個標註本身不穩定
用一個我自己都重現不了的刻度去評模型，等於假裝精確

三級的好處是每一級都綁定一個**可操作的決定**：去面試、要補強、不要投
評估的時候直接算三分類的準確率就好，Day 25 建規準時不用再重新定義一次

### 為什麼是 24 組，不是 60 組

10 份履歷 × 6 份職缺是 60 種組合，但我只標了 24 組

剩下的 36 組大多沒有資訊量
「前端 2 年 vs 資料平台職缺」這種，答案是 weak，模型答對也證明不了什麼

我挑的原則是：**同一個職缺配上強中弱不同的履歷**，或是**同一份履歷配上不同難度的職缺**
所以兩個後端職缺最密集：資深後端五組（8 年 strong、4 年 partial、1 年 weak、轉職者 weak、SRE partial），初階後端六組
這樣才看得出模型的判斷有沒有隨著條件單調變化，而不是隨機

24 組的分布是 strong 5 組、partial 10 組、weak 9 組
partial 最多是故意的。strong 跟 weak 其實不難判，難的永遠是中間那段

## 怎麼生出來的

手工訂規格，模型寫內容，我逐份校對

先把每份履歷的規格寫死：職能、年資、要埋哪幾個 `quality_issues`、哪些技能刻意不能出現
然後讓模型照規格產出履歷內文，我再一份一份檢查

校對主要在抓三件事：

- **缺陷有沒有被模型「治好」**。要一份籠統的履歷，模型很容易寫著寫著就補上具體數字，因為它被訓練成要寫得好
- **有沒有跑出真實公司名**。全部換成虛構的，而且六個職缺的公司名跟履歷裡的前東家互相對得上，看起來才像同一個世界
- **聯絡方式有沒有漏網**。全部檢查過是 `@example.invalid` 與 `0900-000-00X`

`expected_matches` 的 24 組全部是我自己讀完標的，沒有讓模型標
理由很單純：**用模型標的答案去評模型，只會評出「跟它自己有多像」**

## 這批資料的天花板

有一件事要先說清楚，免得後面自己騙自己

模型生的履歷太乾淨了
段落整齊、時間格式統一、沒有錯字、沒有把兩段經歷寫在同一行

真實履歷不長這樣。真實履歷是 PDF 轉出來的爛排版、表格被壓成一串、日期格式一份一個樣

所以這批資料能測的是**理解與判斷**，測不了**解析的韌性**
Day 08 做 PDF 上傳時會另外處理格式的混亂，那是不同的問題，不該混在同一批資料裡解

另一個限制是 `expected_matches` 是我一個人標的
它代表「一個工程師會怎麼判斷」，不代表產業共識。模型跟我不一致的時候，第一步永遠是回頭看是不是我標錯了

## 今天的結論

這篇沒有跑任何一次模型，repo 裡多的全是純文字檔

- `data/resumes/sample-*.txt` 十份虛構履歷，每份都帶著刻意設計的缺陷
- `data/jobs/sample-job-*.txt` 六份職缺，必備條件都編號，之後可以逐項對照
- `data/index.json` 資料集清單 + 五種缺陷分類 + 三級適配量表 + 24 組人工標註答案
- `data/resumes/.gitignore` 先全擋再白名單，防止真實履歷手滑進版控

從明天起，「我覺得變好了」這句話有辦法被驗證了

版本：Python 3.12.10、資料集 v1.0（10 履歷 / 6 職缺 / 24 組期望結果）
